# 为什么做独立 Agent，而不是直接用 Open WebUI 集成？（2026-11-24）

## 你的问题

"做这个 Agent 有意义吗？它好像能打开 WebUI，我从那里面集成不行吗？"

## 诚实结论

**两者定位不同，不是替代关系。** WebUI 是"聊天的网页界面"，这个 Agent 是"能动手的本地执行引擎"。
你真正看重的那些能力（后台命令行闭环、系统控制、自治、权限门控、多模型协同、Manim 动画，
恰恰都在 WebUI 里没有、只有独立 Agent 才做得到。

## 实测对比

| 能力 | Open WebUI | 本 Agent |
|---|---|---|
| 模型对话 / 切换 / RAG 知识库 | ✅ 强项 | ✅ 也有（本地 FTS5） |
| 网页界面 / 多用户 / 美观 | ✅ 现成 | ⚠️ 桌面 GUI，界面朴素 |
| 联网搜索 | ✅（web_search） | ✅（Bing + web_fetch） |
| 执行代码 | ⚠️ 仅 code_executor（沙盒 Python） | ✅ Python/C/C++/Node/Shell/PowerShell 编译运行（`compile_run`） |
| **后台命令行闭环**（自己输命令→读退出码/输出→失败改命令重试→无需人操作） | ❌ 没有 | ✅ 核心能力（run_command + 自主执行铁律） |
| 读写本机任意文件 / 建虚拟环境 / Git 操作 | ❌ 受限 | ✅ 完整文件工具 + venv_manager + Git 面板 |

| 固件/启动项/抓包（授权门控） | ❌ | ✅ 默认关闭、开关授权 |
| 自治闭环（L3 计划 / L4 验收换路径 / L5 围栏自治） | ❌ | ✅ |

| Manim 数学动画 / Mermaid 流程图 / 数据图表弹窗 | ❌ | ✅ 全部集成并实测 |
| 桌面级交互（拖放附件、图片预览、系统播放器等） | ❌ 网页内 | ✅ 原生桌面 |
| 权限可控（每个高危操作逐次确认 + GUI 开关） | ⚠️ 弱 | ✅ 完整门控 |

## 为什么 WebUI 做不了"后台命令闭环"

WebUI 本质是**浏览器里的聊天应用**，它的 code_executor 在服务端沙盒里跑一段 Python 就结束了，没有：
- 持续的多步 ReAct 循环（思考→工具→观察→再思考，直到完成）；
- 读取真实退出码并自主判断成败、失败后改命令重试的机制；
- 对**本机桌面**的控制（它没有你的 Windows 会话权限）。

这正是你第 3 点强调的"非常重要"的功能——它必须是一个有状态、能循环、能控制本机的 Agent 运行时，
WebUI 的服务端架构天然不适合做这件事。

## 那 Agent 是不是该抛弃 WebUI？

**不是，两者可以共存，各取所长：**

- **WebUI**：适合日常问答、用网页界面和 RAG 知识库、多模型快速切换体验、手机/多设备访问。
- **独立 Agent**：适合需要它真正动手干活的场景（批处理文件、自动化、编译运行、系统控制、长时间自治任务、做动画/图表）。
- 你现在桌面上两个都有，按需用即可。Ollama 是两者共用的模型底座，模型只加载一份。

## 未来如果要融合

可行方向（不作为当前承诺）：让 WebUI 通过 MCP/HTTP 调用这个 Agent 的执行能力，
即"WebUI 当前端聊天壳，Agent 当后端执行引擎"。但这是额外工程，当前两套各自可用、互不干扰。
